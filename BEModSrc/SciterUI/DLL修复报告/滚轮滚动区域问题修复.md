

# Sciter 5.0.3.15 x86 滚轮逆向、修改与恢复记录

## 1. 这份目录是什么

## 2. 最终目标与取舍

目标不是重写 Sciter 的整个滚动系统，而是仅在 DLL 内部速度向量的两个确定位置做最小替换：

1. 纵向滚轮输入进入速度向量时，统一输入、修正反向残余速度。
2. 每一动画 tick 衰减纵向速度时，缩短松手后的尾巴。

最终版刻意不保留下列早期实验：

- C++ 宿主中的 `WM_APP` 自定义滚动驱动；
- 依赖宿主定时器或消息频率的节奏状态；
- x86 旧版的“三档”累加/加速策略；
- 对边缘、回弹、滚动跨度的额外干预；
- 曾测试过的反向 55%、70%、90% 系数。

这些曾经是为了找手感而做的实验，彼此会叠加、且 x86/x64 难以完全同步。当前版的反向规则不是“反向保留百分比”，而是更可预测的 `Vnew = input`：方向真的改变时直接清掉旧纵向速度，只用本次输入重新开始。

## 3. 从干净 DLL 开始的逆向定位

### 3.1 认可的输入与验证方式

分析以 `C:\Users\admin\AppData\Local\Temp\be\sciter_5.0.3.15.dll` 为唯一干净 x86 输入。生成器首先计算 SHA-256，必须严格等于本说明顶部的 `clean` 哈希，否则拒绝输出。这样可以避免把补丁继续叠到已改 DLL 上。

静态验证使用 x86 cdb 附加 `HoldLoad32.exe`，由它 LoadLibrary 当前 DLL；验证重点是新增节中的反汇编、跳转落点、IAT 调用和未覆盖原函数尾部，而不是仅以“文件生成成功”作为判断。

### 3.2 原始输入路径

在干净 x86 DLL 中定位到滚轮速度写入函数：

```text
RVA 0x00123965
原始开头：55 8B EC F3 0F ...
```

关键语义由 cdb/IDA 对照确认：

```text
input.x * stock_scale  -> velocity.x [ecx+20h]
input.y * stock_scale  -> velocity.y [ecx+24h]
```

原 DLL 的比例常量在 `RVA 0x00543A6C`，值为原始 `1/24` 缩放。补丁不伪造全新的坐标系统，而是继续使用这项原始缩放，因此 `+90` 的归一化输入进入速度前会先变为 `+3.75`。

### 3.3 原始纵向 tick 路径

纵向速度的衰减点位于：

```text
RVA 0x0012402A
原始被替换的 16 字节：
movss xmm0,[esi+24h]     ; 当前纵向速度
lea   ecx,[ebp-10h]
movaps xmm1,xmm0
mulss xmm0,[esi+30h]     ; Sciter 原生纵向阻尼
```

原函数后续入口为 `RVA 0x0012403A`。补丁执行完新的阻尼选择后，会恢复被覆盖的三条准备指令和 `push ecx`，再跳回该入口。因此不改变随后原有的边界计算、绘制、回调及其它轴逻辑。

## 4. 当前 x86 补丁如何写入 DLL

生成器自己解析 PE32 节表、检查有无节表空间，随后在文件末尾增加一个 `.fx01` 节，权限为可读、可写、可执行。新增节的相对布局固定为：

```text
section + 0x000 : 输入 trampoline
section + 0x180 : 纵向 tick trampoline
section + 0x300 : 状态数据
                  +0x00 DWORD lastInputTickMs
                  +0x04 float TailDamping = 0.60
                  +0x08 float VerticalInputGain = 1.00
```

输入 hook 用近跳转从 `0x00123965` 转入新增节；tick hook 用近跳转从 `0x0012402A` 转入 `section + 0x180`。生成器会先逐字节检查两处原始字节，若干净 DLL 版本不一致则直接报错。此前输入代码增长时，曾发现其超过旧的 `+0x80` 边界并覆盖 tick 代码；最终布局已经扩至 `+0x180/+0x300`，且源码中有长度保护，避免再次互相覆盖。

## 5. 当前输入算法

### 5.1 纵向幅度归一化为 ±90

读取原始 `input.y` 的 IEEE-754 位模式：

- 若绝对值为 0，保留 0；
- 否则只保留原符号位，并将绝对值替换为 `90.0f`（位模式 `0x42B40000`）。

因此每一个非零纵向滚轮包在该版中都会成为 `+90` 或 `-90`，不会直接受单个包原始幅度和鼠标滚轮系数抖动影响。随后仍乘 Sciter 原始 `1/24`，再乘 `VerticalInputGain = 1.00`。之前短暂测试过冲量额外提高 5%，最终已经取消；当前增益确实为 1。

### 5.2 反向规则

补丁比较“本次非零输入的符号”和 `velocity.y` 的符号：

- 同方向：保持原生相加，连续输入仍能累积；
- 方向相反：先将 `[ecx+24h]` 写为 0，再执行原来的加法；
- 输入为 0：保持原函数对 0 的行为。

等价关系：

```text
同向：Vnew = Vold + input
反向：Vnew = 0 + input
```

这样不会出现把旧正向速度翻成反向再叠加、造成往返时突然爆发或向单一方向漂移的问题。

## 6. 从“5 帧”到“80ms”的尾部算法

历史上先使用“每次输入后保护 5 个原生 tick”的方案：这五次 tick 保持 `[esi+30h]` 原生阻尼，之后才使用更强的 `0.60`。它在本机手感可用，但帧率、UI 繁忙程度和计时节奏不同的机器上，5 个 tick 对应的真实时间并不相同，连续滚动能否叠加也会不同。

当前版改为真实时间窗口：

```text
每次进入滚轮输入函数：lastInputTickMs = GetTickCount()
每次纵向 tick：elapsed = GetTickCount() - lastInputTickMs

elapsed <= 80ms : 使用原生 [esi+30h] 阻尼
elapsed >  80ms : 使用 0.60 阻尼
```

`DWORD` 减法在短时间窗口内自然可处理 `GetTickCount` 32 位回绕。调用的是干净 DLL 已有的 `KERNEL32!GetTickCount` IAT 槽（RVA `0x00492158`），没有新增导入表项或外部 DLL 依赖。x86 代码在 API 调用前保存用于 ASLR 相对寻址的 `EDX`，调用后恢复它，再继续原逻辑。

| `VerticalInputGain` |           `1.00` | 没有额外冲量提升                 |
| 反向速度            |       清零旧速度 | `Vnew=input`                     |

## 2. 版本演进和最终取舍

早期 x86 与 x64 曾各自有多轮试验，包含反向保留 55%/70%/90%、尾部 2/3/4/5/6/10 帧、不同阻尼、5% 冲量、跨度系数、宿主 WM_APP/计时器以及 x86 三档策略。它们用于观察问题：反向时卡住、突然爆发、连续上下时单向漂移、尾部画面模糊、不同机器手感不同。

最终决定是把两端收敛到同一份最小逻辑，并从干净 DLL 构建：

1. 每个非零纵向包归一化为 `±90`。
2. 同向保留原生累加。
3. 反向丢弃残余速度，直接以本包重启（`Vnew=input`）。
4. 近期输入继续使用 Sciter 原生阻尼。
5. 松手后才使用 `0.60` 快速收尾。
6. 近期输入窗口由“5 帧”改为固定 `80ms`。

因此当前源里**没有**“反向 55%/70%/90%”乘数；那些属于已放弃的旧分支，不能据此判断当前 DLL 行为。

## 3. 从干净 x64 DLL 逆向出的两个锚点

### 3.1 纵向输入速度写入

干净 DLL 的图像基址为 `0x180000000`。已确认的纵向输入锚点：

```text
VA 0x1801A45F0
原始指令：movss xmm2, dword ptr [r9+4]
继续地址：0x1801A45F6
```

`[r9+4]` 是原始纵向输入；下游原生代码将其叠加进 `[rcx+34]` 的纵向速度。输入 hook 只替换这一条被覆盖指令，处理完后跳回 `0x1801A45F6`，让原生 x 轴逻辑和最终 y 加法保持原样。

### 3.2 纵向 tick 阻尼

已确认的纵向阻尼锚点：

```text
VA 0x1801A4DEF
原始指令：mulss xmm0, dword ptr [rbx+40]
继续地址：0x1801A4DF4
```

在这个位置，`XMM0` 是待写回的纵向速度，`[rbx+40]` 是原生纵向阻尼。原函数在 hook 前已经准备了 `RCX = RDI`，供紧接着的虚函数调用使用；这一点后来成为排查 x64 崩溃的关键。

上述地址由 IDA/cdb 对照验证。静态 cdb 检查的目的包括：确认 hook 的原始字节仍匹配干净文件、跳转返回地址正确、IAT 相对调用落点正确，以及新代码没有覆盖原函数未替换部分。

## 4. PE32+ 写入结构

生成器解析 PE32+ 节表，校验干净 SHA-256，再增加 `.fx64` 节，权限可读/可写/可执行。布局：

```text
section + 0x000 : 纵向输入 trampoline
section + 0x200 : 纵向 tick trampoline
section + 0x400 : 状态数据
                  +0x00 DWORD lastInputTickMs
                  +0x04 float TailDamping = 0.60
                  +0x08 float VerticalInputGain = 1.00
```

输入 hook 和 tick hook 均先核验干净原始指令，再写 5 字节相对跳转；若 DLL 版本不同，生成器拒绝操作。新增节是独立的，不会覆盖原始节或原有导入表。

## 5. 当前输入与反向算法

### 5.1 ±90 归一化

hook 读取 `XMM2` 中的 `input.y`：

- 绝对值为 0：保持为 0；
- 非零：保留符号位，将绝对值改为 `90.0f`，即位模式 `0x42B40000`。

之后本包仍走原生下游的缩放和累加，额外 `VerticalInputGain` 固定为 `1.00`。此前测试过额外冲量提高 5%，当前已取消，不存在隐藏的加速增益。

### 5.2 反向重置

非零输入时比较其符号与 `[rcx+34]` 旧速度符号：

```text
同向：Vnew = Vold + input
反向：Vnew = 0 + input
```

这避免反向时旧速度残留、反向慢速拖行后又突然爆发，或连续上下后位置总向某个方向偏移。它不等同于旧试验中的“反向按 55%/70%/90% 继承速度”。

## 6. 5 帧方案为什么被改成 80ms

初版尾部规则是“每个输入包将计数设为 5；接下来的 5 个 native tick 使用 `[rbx+40]` 原生阻尼；之后使用 0.60”。这在固定机器上手感稳定，但不同 Win11 机器的 UI tick 间隔、繁忙程度与渲染节奏不同，5 个 tick 的真实时长不是固定值。它会影响上一包余速能否参与下一包的累加，也就是实际加速度。

当前规则：

```text
输入时：lastInputTickMs = GetTickCount()
tick 时：elapsed = GetTickCount() - lastInputTickMs

elapsed <= 80ms : mulss xmm0,[rbx+40]  （原生阻尼）
elapsed >  80ms : mulss xmm0,0.60      （快速收尾）
```

使用的是干净 x64 DLL 已有的 `KERNEL32!GetTickCount` IAT 槽：

```text
ImageBase + 0x006182B8
```

没有新增导入，也不需要 C++ 宿主发送 WM_APP。

## 7. x64 崩溃的定位与修复

80ms 版第一次生成后，x86 正常，但 x64 一滚动即崩溃。cdb 静态分析 tick 原函数上下文发现：在被替换的 `mulss` 之前，原代码已经执行 `mov rcx,rdi`；在 `mulss` 之后，它依赖这个 `RCX` 作为下一次虚函数调用的 `this` 参数。

`GetTickCount` 遵循 Windows x64 ABI，会合法改写易失寄存器 `RCX`。初版 tick trampoline 只保存了 `XMM0`，没有保存 `RCX`，导致回到原代码时虚调用使用错误对象地址，从而在滚动 tick 中崩溃。

最终 tick trampoline 的保护顺序是：

```text
sub rsp,30h                  ; 对齐并预留 32 字节 shadow space
movss [rsp+20h],xmm0         ; 保存待衰减的纵向速度
mov   [rsp+28h],rcx          ; 保存原代码已准备好的 this 指针
call  qword ptr [GetTickCount IAT]
movss xmm0,[rsp+20h]
mov   rcx,[rsp+28h]
add rsp,30h
```

cdb 已对当前最终 DLL 确认这一序列存在，随后才计算 `elapsed`、选择 `[rbx+40]` 或 `0.60`，并跳回 `0x1801A4DF4`。输入 trampoline 也会保存/恢复 `RCX` 与 `R9`，因为它同样调用 `GetTickCount` 后还需要它们分别访问速度对象和输入结构。

这就是本目录 `fixed01` 哈希与前一次“80ms 初版”不同的原因；本目录的 DLL 是已修复 RCX 崩溃后的最终版本。
