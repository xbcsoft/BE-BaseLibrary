# 文本扩展函数开发规范（白易0.6）

> 适用范围：白易·`中文核心扩展/文本操作.cpp`、`Win32基础模块/...`及其他扩展模块中的文本处理函数。

---

## 1. 文本类型别名与平台语义

`StrPlat` 类型在白易中是与编译平台绑定的字符集的别名字符串类型：

| 平台 | `StrPlat` | 编码 |
|---|---|---|
| Windows | `StrW` | UCS-2 / UTF-16 |
| Linux   | `StrA` | UTF-8 |

> **结论**：在 Windows 上开发时，`StrW` 是一等公民，函数至少必须实现 W 版（A 版根据实际需求决定是否实现），Linux 的情况上反之亦然。
>
> **补充核心规定**：白易框架下，**A 版（StrA）任何平台均始终视作 UTF-8字符串**。
>
> 在使用了白易模块后，会对当前VS工程引入**BE.props**配置，这使得 Windows 上通过编译器指令(/utf-8)强制字符串的字面量为 UTF-8字符集，使得 `StrA` 代表的 **A 版 **内容实质变更为 UTF-8（其实这个A也可以有另一层解读——只要兼容ASCII即可，而不一定要是ANSI），并在Win32平台上通过全局对象的初始化让其在main函数执行之前预先调用**SetConsoleOutputCP(CP_UTF8)**确保了控制台输出的一致性。
>
> **这一设定其实也在于利好AI**：消除AI对源文档编辑、调试输出控制台编码识别总是UTF-8的心智负担。
>
> 原则上已经砍掉ANSI的设定，若仍坚持使用Windows A版API务必自行设计U8ToCP_ACP的转码函数。

### 为何 StrPlat 使用 `_WIN32` 而非 `_UNICODE`

`StrPlat` 的平台分支**必须由 `_WIN32` 宏控制，而不是 `_UNICODE`**。这不是细节偏好，而是一条具有法理意义的架构约束。

**`_UNICODE` 的本质是 MSVC 项目的"字符集配置开关"**，用于切换 Win32 SDK 中 `CreateWindow`、`MessageBox` 等宏展开为 A 版还是 W 版。它**不代表当前平台，而是代表当前项目对 Win32 历史遗留双字符集体系的选择**。

若以 `_UNICODE` 驱动 `StrPlat`，将产生如下法理漏洞：

- 模块作者以 `_UNICODE` 编译lib模块，生成了只含 W 版符号的二进制；
- 使用方在 VS 中假定会将项目切换为"多字节字符集"（不定义 `_UNICODE`），此时 `StrPlat` 变为 `StrA`，链接器去找 A 版符号，却发现根本不存在——报"符号未找到"，此时模块作者是否需要再编译一套A版？

根因在于：`_UNICODE` 允许"同一 Windows 构建中二选一"的二义性，而 `_WIN32` 是**平台身份标识**，绑定的是操作系统内核级的事实，不受任何项目配置影响。
现在白易规范在 Windows 上发布的二进制模块中，**对于跟涉及系统调用相关的设计钦定为W 版（至少要实现这一套）**，对于历史遗留的 ANSI 版的平行符号可选择性支持（即Win32 系统 API 的那套 `CreateWindowA / CreateWindowW` 双字符集接口正是历史遗留产物，白易的模块设计哲学不应重蹈此覆辙）。

**故从法理上，每个平台上至少编译一套平台钦定的唯一字符集**：

| 平台    | 唯一合法的原生字符集            | 宏依据      |
|---------|-------------------------------|------------|
| Windows | W（UTF-16，系统 API 原生）      | `_WIN32`   |
| Linux   | A（UTF-8，libc 原生）           | 非 `_WIN32` |

> 当然，只要VS工程上统一设置Unicode字符集后，<tchar.h>中_T("...")规定平台级字符串依旧有效，此时它仅作为平台区分（因为Linux上压根就没这个头文件 and 宏），故在白易框架内不视为A版或W版字符集传统工程层面的设定。

> 另外 ，`StrPlat`类型一般是给到中间通用层的兼容系统调用设计（👉[见4.2中的示例](#4.2 跨网络等与平台无关业务场景：以 StrU8 为接口)），若非来到系统调用这个层面的封装则大不可必使用此类型（本身就只在单一平台上设计的模块只需使用本平台钦定的类型即可）；
> 而对于跨平台字符集处理函数接口的高级层面设计更推荐👇1.2章节有损 与 2.0+章节无损 设计方案





## 2. 跨平台的字符集处理函数引出接口规范

为了兼顾 IDE 的友好性、接口的统一性以及跨平台/跨字符集的明确性，白易推荐使用 **“1+1+1”** 的底层通用模板+ 同名模板 + 非模板作为公版重载函数（对于二进制发布还需再进行一层模板显式实例化）。

无论模块以 **源码** `.cpp` 还是 **编译二进制库** `.lib` 的形式发布，处理 A/W 双字符集的函数均应遵循以下结构：

- **公版公开接口（A版 / 默认版）**：非模板函数，接受 `StrA`。它是唯一的正式公版接口，承载**唯一一份**完备的注释文档。
- **显式版本接口（W版 / U8版等）**：**同名模板函数**，接受对应字符集类型（如 `StrW`）。通过显式模板参数（如 `<W>`）调用。



### 2.1 常见的四类定义模式

根据代码的**分发形式**（源码/二进制）以及 **A/W 逻辑关联度**，通常分为以下四类定义模式：

#### 第一类：源码发布型（底层共用逻辑）
适用于逻辑完全一致且通过源码分发的场景。之所以仍需采用 **“1+1+1”** 结构，核心原因在于 **C++ 模板在参数推导出对应具体重载版本之前，无法直接触发隐式转换**。
通过非模板的 A 版重载，可以让 `char*` 字面量等自动转换为 `StrA`，从而为用户提供最自然的调用体验；而 W 版接口采用模板形式则纯粹是为了引入 `<W>` 这一防呆标记，尽管它是模板函数，但其参数类型依然被固定为具体的 `StrW`，让W 版接口也能够像普通函数一样，自动触发 `charW*` 等字面量向 `StrW` 的隐式转换，极大地方便了调用。

```cpp
// 底层统一模板实现
template<class StrT>
size_t _取文本长度(const StrT& 文本数据) {
	return 文本数据.len(); 
}

// W版接口：模板形式引出，由于模板优先级总是最低，需通过 <W> 显式触发
template<class StrT=W>
size_t 取文本长度(const StrW& 文本数据) { return _取文本长度(文本数据); }

// A版接口：非模板重载，作为唯一的正式文档入口
/**取文本长度
 * @param 文本数据 
 */
size_t 取文本长度(const StrA& 文本数据) { return _取文本长度(文本数据); }
```

#### 第二类：二进制发布型（底层共用逻辑 + 显式实例化）
适用于需隐藏库逻辑或以 `.lib` / `.dll` 二进制形式分发的场景。需配合 `_BETPL_DEF` 和显式实例化。

```cpp
// 内部实现：加上 _BETPL_DEF，生成的头文件中将仅保留声明，隐藏函数体
template<class StrT> _BETPL_DEF
size_t _取文本长度(const StrT& 文本数据) { 
	return 文本数据.len(); 
}

// 【核心步骤】为 W 版提供显式实例化，确保二进制符号导出（源码分发可省）
template size_t _取文本长度(const StrW&);

// W版接口 (同上)
template<class StrT>
size_t 取文本长度(const StrW& s) { return _取文本长度(s); }
// A版接口 (同上)
size_t 取文本长度(const StrA& s) { return _取文本长度(s); }
```

#### 第三类：二进制发布的逻辑独立型（A/W 逻辑差异巨大）
适用于 A/W 实现完全不同的场景。即便逻辑无法抽取公用底层模板，若以二进制分发方案发布时，W 版底层实现依旧建议通过 `_xxx` 形式进行内部封装与显式实例化包装（即保持 **“1+1+1”** 结构+模板显式实例化），以便通过 `_BETPL_DEF` 实现生成的头文件对函数体细节的隐藏。

```cpp
// W版底层实现：单独针对 StrW 的实现，但在 .cpp 中标记为模板
template<class StrT> _BETPL_DEF
StrW _复杂处理(const StrW& s) { /* UTF-16 专属逻辑 */ return ...; }

// 如果是二进制分发，依然需要对应的显式实例化（源码分发可省略）
template StrW _复杂处理<StrW>(const StrW&);

// W版引出接口：通过模板包装，维持 <W> 调用习惯
template<class StrT>
StrW 复杂处理(const StrW& s) { return _复杂处理<StrW>(s); }

/**复杂处理*/
// A版引出接口：直接实现
StrA 复杂处理(const StrA& s) { /* A版专属逻辑 */ return ...; }
```

#### 第四类：源码发布的逻辑独立型（A/W 逻辑差异巨大）

适用于逻辑无法统一且通过源码发布的场景。由于无需考虑逻辑隐藏，可直接在引出接口中进行独立实现。

```cpp
// W版引出接口：直接在模板内实现逻辑，维持调用端 <W> 习惯
template<class StrT>
StrW 复杂处理(const StrW& s) {
	/* W版专属逻辑实现 */
	return ...;
}

/**复杂处理*/
// A版引出接口：直接实现
StrA 复杂处理(const StrA& s) {
	/* A版专属逻辑实现 */
	return ...;
}
```

#### 第五类：Win32 特有以 W 版为核心，A 版转码引出的封装模式
适用于 Win32 平台特有、底层调用原生 W 版 API，但需要向上层同时暴露 A版 (UTF-8) 和 W版 (UTF-16) 接口的场景。

- **设计准则**：
  1. 底层实现一个内部函数 `_函数名`，仅接收和返回 W 版字符串或 W 版相关容器。
  2. 暴露 `template<class StrT = W>` 的 W 版同名模板接口，直接转发给底层内部函数。
  3. 暴露普通 `StrA`（A版/公版）同名接口，在内部调用底层内部函数并对入参/出参及容器元素进行 W ->UTF-8 转码。
- **典型范例（以 `取命令行` 实现为例）**：
  ```cpp
  // 1. 底层 W 版核心实现
  StrW _取命令行(Arraybe<StrW>& 命令行数组) {
  	命令行数组.clear();
  	int argc = 0; LPCWSTR cmd = GetCommandLineW();
  	LPWSTR* argv = CommandLineToArgvW(cmd, &argc);
  	// ... 提取命令行参数文本ret
  	return ret;
  }
  
  // 2. W 版引出接口：同名模板函数，允许 <W> 显式触发
  template<class StrT = W>
  StrW 取命令行(Arraybe<StrW>& 命令行数组) { 
  	return _取命令行(命令行数组); 
  }
  
  // 3. A 版引出接口：公版接口，负责做 UTF-8 互转适配
  StrA 取命令行(Arraybe<StrA>& 命令行数组) {
  	命令行数组.clear();
  	Arraybe<StrW> arrW;
  	StrW retW = _取命令行(arrW);
  	for (auto& wStr : arrW) {
  		命令行数组.push(WtoU8(wStr));
  	}
  	return WtoU8(retW);
  }
  ```

#### 统一调用方：

```cpp
取文本长度("hello");          // 匹配 A 版（默认为 UTF-8 字节处理）
取文本长度<W>(_W("hello"));   // 显式指定 W 版（注意L在Linux上是UTF32，_W可统一UTF16）
```

> **备注：白易插件源文件自动化生成头文件 (Source to Header) 规则说明：**
>
> - **常规函数**：自动化生成时会去除其函数体定义，仅保留函数声明。
> - **模板函数**：出于模板本身不具备编译单元，默认会完整保留整个函数体定义。
> - **`_BETPL_DEF` 标记**：若对模板函数加上此标记，插件将采取与普通函数相同的策略——即在生成的头文件中**删除函数体，仅保留声明**。这通常用于配合 `.cpp` 中的模板显式实例化，以实现二进制分发时的逻辑隐藏。

#### 方案核心优势

1.  **文档维护简化对IDE友好**：由于 A/W 版本完全同名，注释文档只需在非模板的 A 版上维护一份，IDE 通常能自动关联到同名函数的公版注释，当在用户输入函数名后，可以通过参数提示列表上下方向键切换查看不同的重载定义（A版那边会有注释）。
2.  **防呆机制（<W> 强制标记）**：如果开发者不显式添加 `<W>`，编译器会默认调用接收 `StrA` 的公版接口。这种设计确保了开发者必须“有意识”地选择 W 版本，降低了隐式字符集混淆的风险。
3.  **解决无参函数识别困境**：像 `取空白文本()`、`字符()` 这种不带参数或参数无法推导类型的函数，传统的重载机制无法区分。通过模板模式，可以使用 `取空白文本<W>(255)` 这种统一的语法来显式指定版本。
4.  **基础类型隐式转换支持**：该方案能自然利用 C++ 隐式转换规则。对于公版接口，可以直接传递 `char*`/`const char*` 字面量（自动转为 `StrA`）；对于 `<W>` 模板，可以传递 `wchar_t*`（自动转为 `StrW`），极大地保持了调用端的代码简洁，无需手动进行类型包装。
5.  **U8 隐式兼容处理**：由于 `StrU8` 可以隐式转换到 `StrA`，在不写任何版本标记时投递 U8 变量会走 A 版处理。这对于大多数面向字节流兼容的通用处理非常友好。
6.  **二进制分发友好 (Binary Friendly)**：通过显式引出 A 版、W版常规函数符号，确保了在 `.lib` / `.dll` 场景下的对符号编译的二进制代码存在性。
7.  **源码分发简化 (Source Optimization)**：若仅以源码分发，可直接去掉 `.cpp` 中的模板显式实例化声明，进一步减少维护工作量。



### 2.2 StrX / c_StrX (通用文本编码传参类型) 的设计与应用

#### 💡 核心设计规范：文件处理与高级 API 的 StrX 优先原则

- **设计指引**：在文本/系统扩展函数 API 设计中，**但凡涉及文件路径相关，或者是不影响性能的高级功能函数参数，均推荐使用 `StrX` / `c_StrX` 进行参数设计**。这样在保证高级功能极简的同时，调用端无需关心编码转换，可直接传入 `StrA`、`StrW`、字面量等。
- **为何不用 AutoStr？**：虽然 `AutoStr` 也具备相同的转换能力，但它是无脑接收一切类型（包括 `RECT`、数组等）的“万能格式化中转站”。如果将其用于文件路径传参，调用端哪怕误传了一个数组也不会在编译期报错。而 `StrX` 继承自 `AutoStr` 并**剔除了万能模板构造**，它在编译期就建立起了“必须是纯文本才能传”的绝对防御。

#### 典范实现：双接口折中替代方案（以`取临时文件名`为例）

在 Win32 系统接口调用中，使用 `StrX` 能极大地简化路径处理，省去繁琐的 A/W 转换与临时变量。这是一种避免到处书写双接口重载的绝佳折中方案：

```cpp
StrX 取临时文件名(c_StrX 目录名 = "") {
	const charW* dir = 目录名;
	charW tempPath[MAX_PATH] = { 0 };

	if (!dir[0]) {
		GetTempPathW(MAX_PATH, tempPath);
		dir = tempPath;
	}

	charW tempFile[MAX_PATH] = { 0 };
	if (GetTempFileNameW(dir, L"TMP", 0, tempFile)) {
		return StrW(tempFile); // 也可以直接返回并隐式向上转换为 StrX
	}
	return "";
}
```

> **备注/说明**：
>
> 1. `c_StrX` 实质上是 `const StrX&` 的别名。白易自 0.6 版本起，正式推荐采用这种具有 `c_` 前缀的常引用命名风格（c_Bytes、c_StrA/W等作为参数传递具备传引用特性而不占据拷贝开销），以保证代码声明的整洁统一 与 性能担当。
> 2. `const charW* dir = 目录名;` 利用了 `StrX` 继承自 `AutoStr` 的隐式转换能力，自动提取或缓存了对应的 Unicode (W版) 字符串指针，供 Win32 API 直接使用。

## 3. 平台目录隔离与宏切换

### 背景

由第 1 节可知，在基于平台的字符集相关处理方案上，Windows 永远是 W，Linux 永远是 A。

正因如此，若某模块只实现了 Windows 上的 W 版，其代码从根本上就是**平台专属**的（来到平台实现后对于Win32平台功能的封装函数无需加前缀W，但引出的字符串接口要与平台相关）

——混入通用目录会产生误导，让使用者误以为它可以在 Linux 下直接编译。正确做法是通过目录结构和宏来显式区分：**目录隔离让"这是哪个平台的实现"在视觉层面就显而易见**，同时让另一平台的实现可以将来独立添加而不影响已有代码。

> **补充说明**：模块入口头文件（统一入口 `.h`）使用 `#ifdef _WIN32` 切换引入各自平台目录，这与 1.1 节中 `StrPlat` 的宏选择原则完全一致——都以 `_WIN32` 作为平台事实依据，杜绝 `_UNICODE` 这类项目配置开关的干扰。

---


#### 完整版目录结构约定（以"Win32/"和"Linux/"目录为例；）

```
中文扩展/
├── 模块入口.h              ← 统一入口头文件（只做 #ifdef 平台分发）
├── Win32/
│   ├── 相关操作.cpp        ← Windows 实现（仅 W 版）
│   └── 相关操作.h
└── Linux/
    ├── 相关操作.cpp        ← Linux 实现（仅 A 版）
    └── 相关操作.h
```

> ##### **#这里【目录名】只是一种软性约定，只需提其是某平台专属相关字样即可，名称本身可随意~**
>

#### 完整版入口头文件示例

```cpp
// 相关操作.h（统一入口，只做平台分发）
#pragma once

#ifdef _WIN32
#  include "Win32/相关操作.h"
#else
#  include "Linux/相关操作.h"
#endif

// 此时 Win32/相关操作.h 中依然应遵循【同名模板 + A版重载】结构
// 但 A 版在 Win32 平台下通常仅作为兼容入口或逻辑转发
```

> 由于已经做了目录隔离，即便是平台各自均使用了同名函数的设计，也只会存在各自平台上的一个符号，故不属于函数重载。



#### **白易Win32模块开发中的特别对待**

若是在**白易模块开发**中，模块入口头文件有明确 **标识** `@platform` **为Win32**，则以上父级目录名作为平台名称的方案可直接砍掉，只需模块入口同级下存放源文件，没那么多规范约束。

## 4. StrU8 — 平台无关的 UTF-8 处理

`StrU8` 继承自 `StrA`，表达"这是 UTF-8 编码"的明确语义（内含对C++20的char8_t*字面量u8"..."支持、专属的U8版字符长度统计与字符索引访问），与 A/W 的平台参考系无关。它的定位是**跨与平台交换层**（网络报文、HTTP 报文体、配置文件等以 UTF-8 为编码约定的场景）。

```
跨平台交换层（StrU8）   →  U8ToPlat / PlatToU8  →   系统调用层（StrPlat / StrW / StrA）
```

> **在 Linux 上**：`StrA` 与 `StrU8` 完全等价，无需任何转换；
> **在 Windows 上**：Win32 API 因接受 `StrW`，需经 `U8ToPlat`（即 `U8toW`）转换后才能传入系统调用。

---

### 4.1 U8 字符串处理函数的命名规则

**U8 专属逻辑同样遵循同名模板规则，使用 `<U8>` 显式调用。只有当 U8 逻辑需要完全独立实现（无法通过 A 版隐式转换覆盖）时，才需定义：**

```cpp
// W 版本
template<class StrT>
size_t 取文本长度(const StrW& s);

// A 版本 / 公版（自带注释）
size_t 取文本长度(const StrA& s);

// U8 版本（同W版一样显式模板标识）
template<class StrT>
size_t 取文本长度(const StrU8& s); // 内部使用 .lenU8() 等实现
```

调用时：`取文本长度<U8>(u8_str)`。如果未定义 U8 专用模板，则会退化尝试匹配 A 版（前提是 StrU8 支持转换并能接受字节语义处理）。

---

### 4.2 跨网络等与平台无关业务场景：以 StrU8 为接口

对于**以 UTF-8 为输入输出**的场景函数（如网络收发、HTTP 解析），直接将 `StrU8` 作为接口类型（由于业务目标它并非是做文本处理的故无需以面向平台为主的命名，且类型语义明确，无需带前缀开头），而后续其内部若有涉及系统调用的则按需转换（**如要设计通用平台统一处理，中间层建议采用StrPlat封装**）：

```cpp
void 创建文件(StrPlat path){
#ifdef _WIN32
    //Windows上：CreateFileW(widePath...)
#else
    //Linux上：open(utf8Path...)
#endif
}

// 面向网络的函数，接口直接用 StrU8
StrU8 处理HTTP文件请求(const StrU8& path, const StrU8& body){
    // 内部需要调用平台 API 时：
    StrPlat path = U8ToPlat(path);       // Windows: U8 → StrW；Linux: 直接返回原值
    // ...相关系统调用（如：上边的创建文件()统一封装方法）
    // 内部处理结束
    StrU8 result = PlatToU8(platResult);    // Windows: StrW → U8；Linux: 直接返回原值
    return result;
}
```

> 这样上层调用者的代码始终只接触 `StrU8`，`StrW` 被完全隔离在实现内部，接口层干净透明。

> **Linux 上的零开销**：`StrPlat = StrA`，而 `StrA==StrU8`（字节层面等价）；
> `U8ToPlat` / `PlatToU8` 在 Linux 上均直接移动返回原值，**不做任何编码转换**，也不产生额外拷贝开销。
